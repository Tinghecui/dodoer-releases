# 智能体把自己的对话挪到干活的地方：转到新分支、收进新项目

状态：2026-11-15。方向和两个决定项用户确认过（第 2 节、第 9 节）：没提交的改动带过去，挪之前弹确认卡片。第 1～4 步一起做在一个 PR 里（`src-tauri/src/commands/relocate.rs`），和设计稿不同的地方见第 11 节。

## 1. 问题

对话属于哪个文件夹，决定了智能体下次连接时在哪个目录干活，也决定了它在侧栏里挂在哪。现在只有人能改这件事：开对话前打开「在新分支开始」，或者事后点「移动到项目…」。

实际用的时候常常是聊着聊着才知道该去哪：

- **转到新分支。** 开对话时没打开「在新分支开始」，聊到一半让智能体「去新分支里做」。智能体自己 `git worktree add` 过去干活，对话却还挂在 `master [root]` 下面。侧栏只能靠 #241（从智能体记录里的工作目录认出 worktree 和 PR）在 master 下面显示一个 PR 标记；下一轮连接时智能体又回到 master 目录。
- **收进新项目。** 让智能体新建一个项目（目录），这个目录侧栏里从来没打开过。智能体在里面干完活，对话还留在原来的项目或聊天里，新项目在侧栏里根本看不到。

智能体现在做不到这两件事，代码里有两处直接挡着：

1. `move_conversations_core`（`src-tauri/src/commands/conversations.rs`）在对话忙时跳过（`MoveSkipReason::Busy`）。智能体调用工具时正处在一轮里，一定是忙的。
2. worktree 不能当移动目标（`f1ad65aa1`，11-12 AI QA 发现「移进去就出不来」）：worktree 里的对话不能移出去（`InWorktree`），所以也不让移进去。

## 2. 用户要的（2026-11-15）

1. 聊到一半让智能体去新分支，它能自己把对话转到那个 worktree 下，效果和一开始就打开「在新分支开始」一样。
2. 让智能体建了新项目，它能把项目加到侧栏，再把自己这个对话放进去。
3. 两件事写进同一份设计。
4. 转分支时，master 上没提交的改动带过去（第 5.3 节）。
5. 挪之前要人点确认卡片（第 5.4 节）。

## 3. 界线：智能体能改界面上的什么

codeg-mcp 已经有会改界面状态的工具（`create_work_task`、`create_automation`、`use_device`），每组都有开关（`companion.rs` 的 `CompanionFeatures::allows_tool`）。这份设计按三层划线：

| 层 | 例子 | 怎么处理 |
|---|---|---|
| 智能体干活产生的事实 | 在哪个分支、开了哪个 PR、后台还在跑 | 不给工具，界面自己读出来（#241、#226） |
| 改**自己这个对话** | 换分支、换项目、换设备、换模型 | 给工具，按功能组开关；改完界面上看得见；碰到用户电脑（`use_device`）或挪动对话、搬改动（本设计）的，先弹确认卡片 |
| 改**对话以外**的东西 | 别的对话、项目设置、智能体配置、关闭或删除 | 不给工具；需要时用 `ask_user_question` 问人，人去点 |

「把项目加到侧栏」严格说是第三层。这里放开，是因为加了限制以后影响很小：只能加本机上已经存在的目录，只是往侧栏添一项，不删、不改别的，加错了人关掉就行。

这条线是为了让操作看得清、改得回，不是安全隔离：服务器上的智能体有 shell，工具列表拦不住真想乱来的进程。

## 4. 共同的机制：本轮结束后再挪

两个工具都先弹确认卡片（第 5.4 节），人同意了再分两半做：

- **立刻做的**：建 worktree / 打开文件夹，侧栏马上出现新的一项；工具把目标路径返回给智能体，这一轮剩下的活它用这个路径干（绝对路径或 `cd`）。
- **本轮结束后做的**：把对话移过去。连接管理器给这个对话记一条「待挪」（目标文件夹 id），等对话真正闲下来（这一轮结束，没有权限请求、后台任务、正在跑的委派、目标挂着；就是 `busy_reason` 为空），走 `move_conversations_core` 同一套挪动：拿锁、`relocate_conversations`、`mark_relocated`、断开空闲连接、广播、改标签页。下一轮在新目录里接着同一个会话，原来的会话记录靠已有的 `origin_cwd` 找回来。

待挪的规矩：

- 一个对话同时只有一条，后来的覆盖前面的。
- 只存在内存里。codeg 在挪之前重启，这条就没了，worktree 或打开的项目还在，对话留在原处；智能体下次调工具再挪一次就行，不做持久化。
- 挪之前对话被人删了、移走了、被待办任务接管了，就放弃，记一行日志。
- 人在这期间点了停止，照样挪：停止只是结束这一轮。

委派出去的子对话跟着根对话挪（`move_conversations_core` 原本就这样）。子对话自己调这两个工具时拒绝：子对话不单独挪。

## 5. 工具组和工具

新功能组 `relocate`（`--features relocate`）。和 `devices` 一样没有设置开关：跑智能体的进程都带上。组里两个工具。

### 5.1 `continue_in_worktree(branch?, path?)`：转到新分支

- 不带 `path`：`branch` 必填（智能体起名）。用 `create_conversation_worktree_core` 从当前 `HEAD` 建 worktree，就是「在新分支开始」开关用的那一条路，位置、`.worktreeinclude`、`init_command` 都一样。
- 带 `path`：智能体已经自己 `git worktree add` 了，就用 `open_worktree_folder_core` 把它登记到这个仓库下面，不再新建。`path` 必须是这个对话所在仓库的 linked worktree。
- 返回 worktree 的路径和分支名，以及「对话会在这一轮结束后转过去」。
- 拒绝的情况：对话所在文件夹不是 git 仓库；对话已经在 worktree 里（worktree 之间不互相挪，和 `InWorktree` 一致）；对话属于待办任务；调用的是委派子对话。
- 「不能移进 worktree」只对这条路放开：本轮结束后的挪动带一个内部标记跳过 `parent_id` 检查。手动「移动到项目…」的限制不变。worktree 里的对话照旧不能移出去：这是单向的，正好就是想要的意思（分支、改动和 PR 都归这个 worktree）。
- master 上没提交的改动带过去，见第 5.3 节。

### 5.2 `adopt_project(path)`：收进新项目

- `path` 是 codeg 所在机器上已经存在的目录的绝对路径。
- 已经是打开的项目：直接用。在历史里（以前关过的）：重新打开。都不是：`open_folder_core` 打开，侧栏马上出现。
- 本轮结束后把对话移进去。聊天对话移过去后变成项目对话（「移动到项目…」原本就这样）。
- 返回项目的文件夹 id、显示名，以及「对话会在这一轮结束后移过去」。
- 拒绝的情况：路径不存在或不是目录；是 linked worktree（让它用 `continue_in_worktree`）；在某个已打开项目的里面（子目录），这时告诉智能体是哪个项目，不另开一个；就是对话现在所在的项目；对话在 worktree 里（`InWorktree`）；对话属于待办任务；调用的是委派子对话。
- 不能用它关闭、改名、删除项目，也不碰别的对话。

### 5.3 转分支时带上没提交的改动

只在 `continue_in_worktree` 新建 worktree 时做；带 `path`（智能体自己建的 worktree）时不搬，智能体自己处理。

- **带什么**：对话所在 checkout 里已跟踪文件的改动（暂存的和没暂存的都算），以及没跟踪、也没被忽略的新文件（`git ls-files --others --exclude-standard`）。被忽略的文件不搬，`.env` 这类靠 `.worktreeinclude` 复制，和「在新分支开始」一样。
- **怎么带**：新 worktree 从同一个 `HEAD` 建出来，所以 `git diff --binary HEAD` 在那边一定打得上：`git apply` 放进去（暂存状态不保留，到那边都是没暂存的改动），新文件逐个复制过去。改动必须还是卡片上列的那些，人看卡片期间变了就不带，让智能体再调一次。
- **核对再清理**：逐个比对 worktree 里的文件和原 checkout 里的一样，然后才把原 checkout 恢复（已跟踪的 `git restore --staged --worktree`，新文件删掉，都只动搬过去的那些路径）。
- **失败就两边都不动**：打补丁、复制、比对任何一步失败，删掉新 worktree 里放进去的改动，原 checkout 不碰，工具返回失败原因。worktree 本身留着，对话也不挪。
- **不用 `git stash`**：stash 栈是同一个仓库所有 worktree 共用的，会碰到别的会话的东西。
- **同一个 checkout 里别的对话的改动**：master 下面常常同时挂着好几个对话，没提交的改动不一定是这个对话做的，搬走了别的对话会发现文件变回去了。所以搬什么由人在卡片上定（第 5.4 节）：卡片列出所有要搬的文件；这个文件夹里还有别的对话正在跑时，卡片上写明是哪几个，并提醒改动可能是它们的。

### 5.4 确认卡片

两个工具调用时都先问人，卡片和 `ask_user_question` 的是同一种（和 `use_device` 的卡片一样，在工具的处理里发问题、等回答，见 `docs/devices.md` 6.2）。每次调用都问，不记「确认过」：每次挪的地方都不一样。

`continue_in_worktree` 的卡片：

- 标题：「这个对话要转到新分支 `<分支名>`」（没给分支名时写「新分支，名字会按对话自动起」；带 `path` 时写那个 worktree 的分支和路径）。
- 说明：回复结束后对话挪到这个 worktree 下面，之后不能再挪回 `<原文件夹>`。
- 有没提交的改动时，列出文件（超过 20 个只列前 20 个和总数）；同文件夹里有别的对话在跑时，写上它们的标题。
- 选项：
  - 「转过去，带上这些改动」（没有改动时就是「转过去」）
  - 「转过去，改动留在原处」（只在有改动时出现）
  - 「不转」

`adopt_project` 的卡片：

- 标题：「把 `<路径>` 加到侧栏，并把这个对话移进去」（已经打开的项目写「把这个对话移到项目 `<名字>`」）。
- 说明：回复结束后对话挪过去；以后可以用「移动到项目…」挪回来。
- 选项：「加进去并移过去」、「只加到侧栏」、「都不要」。

工具返回人选了什么。选「不转」「都不要」时什么都不做，工具告诉智能体「用户没同意」；「只加到侧栏」时打开项目但不挪对话。

人没回答、这一轮被停止或断线时当作没同意。卡片在等回答期间，侧栏照常显示「等你回答」的黄标（#127）。

如果在工具处理里接不上卡片，退一步和 `docs/devices.md` 第 14 节一样：工具先返回「要先问用户」和卡片该写的内容，由智能体调 `ask_user_question`，再带着答案调一次。那样服务器拦不住「没问就挪」，只当临时方案。

### 5.5 写在工具说明里的规矩

- 只在用户要求、或者用户同意了你的提议时调用；不要为了临时看一眼别的目录就挪。
- 调用后这一轮用返回的路径干活；下一轮会自动在新目录里。
- 被拒绝时把原因告诉用户，不要绕过去（比如自己去改数据库）。

## 6. 界面

- 工具调用在对话里显示成普通的 MCP 工具调用，写出目标路径。
- 确认卡片和 `ask_user_question` 的卡片一样显示在对话里，等回答时侧栏有「等你回答」的黄标（#127）。
- 侧栏：人同意后，打开文件夹 / 登记 worktree 时立刻出现新的一项（已有的 `folder://changed`）；本轮结束挪完，对话行跑到新位置（已有的移动广播）。
- 待挪期间不加新的界面状态，挪完也不插系统提示（第 11 节）。
- 改回去：收进新项目的，人用「移动到项目…」挪回去；转到 worktree 的，按现有规矩不能挪出去（卡片上写明了）。不为这个功能单独加撤销。

## 7. 不做的

- 不给智能体关闭、删除、改名项目的工具，也不给挪别的对话的工具。
- 不记「确认过」：每次调用都弹卡片。
- 不在卡片上逐个勾选要搬的文件：要么全带，要么全留。按对话分哪些改动是谁的，以后需要再说。
- 不支持挪到别的电脑上的目录：这里的路径都是 codeg 所在机器上的。
- 不自动跟随：智能体只是 `cd` 进了别的目录，不会自动挪对话，必须调工具。#241 的被动显示照旧。

## 9. 用户定的（2026-11-15）

1. **转分支时，master 上没提交的改动带过去。** 做法见第 5.3 节；卡片上可以选「改动留在原处」。带 `path`（智能体自己建的 worktree）时不搬。
2. **挪之前弹确认卡片。** 两个工具都弹，每次都弹，见第 5.4 节。

## 10. 验收

1. 在 `master [root]` 下的对话里说「去新分支做」，智能体调 `continue_in_worktree`；弹卡片，点「转过去」；侧栏马上出现新 worktree；回复结束后对话挪到 worktree 下面；下一轮 `pwd` 是 worktree 目录，前面的上下文还在。
2. 同上，但智能体先自己 `git worktree add` 再带 `path` 调用：卡片写的是那个 worktree；不新建，登记后挪过去。
3. 先让智能体在 master 上改两个文件、建一个新文件，再转分支：卡片列出三个文件；点「带上这些改动」后 worktree 里有这三处改动、master 干净；另起一次点「改动留在原处」，master 的改动不动。
4. 让搬改动中途失败（测试里在打补丁、复制、比对三处分别注入失败）：两边都不动，工具说清楚原因，对话不挪。
5. master 下另一个对话正在跑时转分支：卡片上写着那个对话的标题。
6. 卡片点「不转」/「都不要」：什么都没建、没打开、没挪；智能体收到「用户没同意」。卡片等回答时点停止：同样当作没同意。
7. 在聊天对话里让智能体建一个新目录项目并调 `adopt_project`：点「加进去并移过去」，侧栏马上出现新项目；回复结束后对话挪进去；下一轮在新项目目录里。点「只加到侧栏」：项目出现，对话不挪。
8. `adopt_project` 给一个已打开项目的子目录、给一个 worktree、给不存在的路径：不弹卡片直接拒绝，原因说得清楚。
9. 在 worktree 里的对话调两个工具都拒绝；待办任务的对话拒绝；委派子对话拒绝。
10. 卡片点了同意、回复结束前人点停止：照样挪。

## 11. 做的时候和上面不同的地方

- **不插系统提示。** codeg 没有往对话里插系统提示的现成机制；挪动靠侧栏里对话换位置、工具返回给智能体的话来体现。
- **`branch` 必填。** 不做按消息自动起分支名：自动起名要拿第一条消息当种子，而这里智能体最清楚该叫什么。
- **没有设置开关。** 和 `devices` 一样，只要进程装上了这组工具就注入。
- **「待挪」不在连接管理器里，** 而是每 2 秒试一次「移动到项目…」那一套（`move_conversation_for_agent`），对话忙就下次再试，24 小时还没挪成就放弃。这样不用碰回合结束的生命周期代码。
- **暂存状态不保留。** 带过去的改动在 worktree 里都是没暂存的。
